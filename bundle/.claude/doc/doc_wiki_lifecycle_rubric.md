# lifecycle ルーブリック — 証拠レベルの判定基準

`lifecycle` の**唯一の正典**。値の一覧・序列・判定手順はすべてここにある。

**参照するときのパスは `~/.claude/doc/doc_wiki_lifecycle_rubric.md`。** skill 本文からはこの絶対パスで読む
（`~/.claude/doc/` は CWD がどのプロジェクトでも解決する。
skill ディレクトリ基準の相対パスは実運用の CWD では解決しない）。配布の仕組みで
`~/.claude/doc` が symlink になっている環境では、編集は配布元の側で行う。

**判定するときは必ずこのファイルを読む。** 各 skill の SKILL.md から基準を引かないこと —— skill は自分の
SKILL.md を最優先で読むので、基準が本文に散ると判定がズレる（それが 2026-08-12 の移行の原因だった）。

## この軸が測るもの

`lifecycle` は「**そのページの主張を、誰が・何をして確かめたか**」を表す。

- ✗ **主観の信頼度ではない**。`high` / `low` のような自己評価は書かない（書く主体が AI なので必ず甘い方へ流れる）
- ✗ **ページの価値ではない**。有用な経験則が `reasoned` に落ちるのは正しい挙動
- ✗ **鮮度ではない**。それは `evidence_at` と stale 判定が持つ
- ○ **行為の事実**。AI は自分がやったことを書く。だから甘く書けず、機械で検査できる

## 序列

| rank | 値 | 主体 | 意味 | 証拠として本文にあるべきもの |
|---|---|---|---|---|
| 6 | `verified` | 人間 | 動かして確かめた | — |
| 5 | `reviewed` | 人間 | 読んで承認した | — |
| 4 | `tested` | AI | **対象を走らせた / 状態を変えて結果を観測した** | 実行したコマンドとその出力・n・日付 |
| 3 | `sourced` | AI | **読み取りだけで確かめた**（コード・ログ・設定・DB の select・一次資料） | ファイルパス＋行番号/関数名/コミットハッシュ、**または**一次ソース URL＋取得日 |
| 2 | `reasoned` | AI | 手元の情報から推論した | （rank 4 / 3 の証拠が主張を支えていない状態） |
| 1 | `draft` | AI | 証拠なし・判定前（**既定値**） | — |

`verified` ↔ `tested`、`reviewed` ↔ `sourced` が対応する（動かした / 読んだ）。

**rank 5・6 は AI が書いてはいけない。** 人間が明示的に承認したときにだけ付く。

## 序列外（rank を持たない。証拠の検査をしない）

| 値 | 意味 | 序列に入れない理由 |
|---|---|---|
| `disputed` | **現在の主張**が後から否定された | 節単位の訂正は含めない。含めると、訂正が丁寧なページほど降格する逆インセンティブが立つ |
| `archived` | 後継ページがある（終端） | `superseded_by` と対で使う |
| `stated` | 一次情報が**人間の逐語**（方針・製品定義・仕様の決定） | 検証の対象ではなく、人間が決めた事実。序列に押し込むと人間由来の一次情報が 3 段下がる。「人間がこう言った」は AI にとっても行為の事実なので、自己申告の禁止と衝突しない |
| `verbatim` | 外部原本の無加工コピー。**改稿しない** | `draft` に落とすと「未完成・要改善」と誤読され、整理作業が原本を書き換える |
| `index` | 自前の主張を持たない（ハブ・索引・ロードマップ・独立節のカタログ・転記中心） | 必要なのは信頼度ではなく鮮度。他ページからの転記で不当に昇格する経路をここで閉じる |

## 値の一覧（機械可読）

<!-- LIFECYCLE_RANKED: verified reviewed tested sourced reasoned draft -->
<!-- LIFECYCLE_UNRANKED: disputed archived stated verbatim index -->

この 2 行は配布元リポジトリのテスト（`tests/test_lifecycle_schema.sh`）が読む唯一の値の出どころ。
**上の表を変えたらここも変える**（テストが表とコメントの不一致を検出する）。

値の命名には制約が 1 つある: **どの値も他の値の部分文字列であってはいけない**。値を読む実装が
すべて自然言語の指示（＝実装するのは毎回別のセッションの LLM）で、`grep 'lifecycle: verified'` と
書かれた瞬間に前方一致の値を静かに取りこぼすため。テストが機械で縛っている。

## 判定の手順

### R1 主張（thesis）を先に書く

**段を選ぶ前に、そのページを読む人が持ち帰る一文を書く。判定はその一文の裏付けだけで決める。**

これが判定の本体。実測ではブレの主因は段の選択ではなく「何が主張か」の同定のばらつきだった。

主張が書けないページは `index`。

### R2 主張の種類が上限を決める

主張が**規範**（〜すべき・この作法が良い）・**因果**（A が B を起こした）・**一般化**（この手法は有効）なら、
**上限は `reasoned`**。本文に実測値があってもそれは前提の確認で、主張そのものを支えていない。

例外: **その効果自体を測った**なら `tested`（A/B 比較・前後比較・復旧確認のいずれか）。

### R3 メタ検証は証拠にしない

実装状況の棚卸し・リンク切れ確認・vault の整合性検証は、そのページの**主題**の証拠ではない。
**他ページからの転記も証拠にしない**（転記で段が上がる経路を閉じる）。

### R4 主張が複数あれば低い方へ丸める

ただし頻出する型は既定を固定して判定を機械化する:

- **実装仕様の記述** → `sourced`（デプロイ後の稼働実測が本文にあれば `tested`）
- **検証記録・調査ログ** → `tested`
- **経験則・作法・因果の考察** → `reasoned`

### R5 判定根拠を frontmatter に残す

```yaml
lifecycle: tested
lifecycle_evidence: "§3 の追試ブートストラップ表"   # 根拠の在処（節見出し・表名）
evidence_at: 2026-08-06                            # 証拠を得た日（ISO date）
lifecycle_changed: 2026-08-12                      # 段が変わった日（ISO date）
```

本文の文字列に依存した判定は次の編集で腐る。`lifecycle_evidence` が指す節が消えたら lint が拾える。

`lifecycle_evidence` と `evidence_at` は **rank 2 以上で必須**（`draft` と序列外では不要）。

**`evidence_at` の取り方**（2026-08-12 の一括移行で 4 件が判断を仰いだ点。順に試す）:

1. **本文が明示している日付**（「2026-08-06 実測」「コミット `abc1234`」の日付）—— これが最良
2. **無ければ frontmatter の `updated`** —— 証拠は更新時に書き込まれたはずなので、`created` より近い
3. **`created` は最後の手段**（そのページが一度も更新されていないとき）
4. **3 つとも無ければ、vault リポジトリの git 履歴から復元する**（2026-08-13 に 6 ページで実施）。
   これは推定ではなく**そのページ自身の事実**なので 5 の禁止に当たらない。復元したら frontmatter へ
   書き戻すこと（次の判定でまた掘らないため）:
   ```sh
   # created = 最古のコミット / updated = 最新の「本文が変わった」コミット
   git -C <vault> log --date=format-local:%Y-%m-%dT%H:%M:%SZ --format='%cd%x09%s' -- <現パス> <旧パス>
   ```
   ⚠️ **一括移動・一括改名のコミットを `updated` に採ってはいけない。** 本文が 1 バイトも変わっていないのに
   「その日に更新された」ことになり、stale 判定が的を外す（subtree add を除外し忘れて 6 ページが揃って
   同日更新に化けた実例あり）。パスが変わっている場合は**旧パスも pathspec に渡す**
   （`--follow` は当てにならない —— 同じファイルで `git log` が 1 件返すのに `--follow` が 0 件を返す実例あり）
5. **他ページや姉妹ページの日付から推定してはいけない。** 同じ改訂波に属するという理由で日付を借りると、
   ページ単位で検算できなくなる。推定するしかない状況なら、それは証拠が特定できていない ＝ `draft` を疑う

⚠️ **でっち上げは禁止。** 日付が分からないまま rank を上げるくらいなら `draft` に留める（迷ったら低い方へ）。

📌 **日付の欠落は「陳腐化を検知できない」だけの問題ではない。** `evidence_at` が決まらないと**この軸を
上げられない**ので、`created`/`updated` の欠落は判定そのもののブロッカーになる。lint が日付欠落を
報告したら、staleness の話だと思って後回しにしないこと。

### R6 他の軸から導出してはいけない

- **`^[inferred]` / `^[ambiguous]` マーカーを判定に使わない**。実測すると読んだ全ページに付いており、
  実測が並ぶページにも 10 箇所以上あった。切り分けの役に立たない。**マーカーは文章の性質の記述であって、
  行為の事実ではない**
- **`provenance` から導出しない**（同じ理由）
- **`base_confidence` から導出しない**。実測で証拠の強さと**逆相関**していた

### R7 段はページの価値ではない

有用な経験則が `reasoned` に落ちるのは正しい。ここで揺れると判定がばらつく。

## 決定表

| ページの型 | 段 |
|---|---|
| 実装仕様の記述 | `sourced`（稼働実測があれば `tested`） |
| 検証記録・調査ログ | `tested` |
| 経験則・作法・因果の考察 | `reasoned`（効果を測っていれば `tested`） |
| 外部ドキュメントの調査 | URL＋取得日があれば `sourced`、無ければ `draft` |
| 人間の逐語の記録 | `stated` |
| 外部原本のコピー | `verbatim` |
| ハブ・索引・カタログ・転記中心 | `index` |
| 上のどれでもなく、証拠が無い | `draft` |

### 実装仕様のページに実測値が混ざっているとき（頻出する境界）

仕様の記述の中に単発の実測値（「35 頭中 10 頭 ＝ 29%」「テストで検証済み」等）が挿し込まれている形は多い。
**ページの主たる性格で決める**（R4 の丸め）:

- 実測が**そのページの主張を支えている**なら `tested`（例: 主張が「この改修は効いた」で、前後比較がある）
- 実測が**仕様の記述に添えられた補足**なら `sourced` に留める（例: 主張が「現行実装はこう動く」で、
  実測値はその一部の裏取り）—— 数値が本文にあることは `tested` の十分条件ではない

判断に迷ったら `sourced`。**「数値があるから `tested`」は最も起きやすい過大評価**で、この境界を曖昧に
したままだと実装仕様ページが軒並み `tested` へ寄る。

### 規約ファイル（rules / CLAUDE.md）から作ったページ（頻出する境界・2026-08-13）

同じ配布物由来でも 2 つに割れる。**一次情報が「人が決めたこと」か「ツールの挙動」かで見る**:

- **人が決めた規範そのもの** → `stated`（例: 言語ポリシー・実装の進め方・ファイル配置の規約）。
  検証の対象ではないので序列に入れない
- **ツール・機構の挙動の記述** → `sourced`（例: read-only の強制範囲・接続先の解決順・許可されるメソッド）。
  規約ファイルに書いてあっても、裏付けはツールの実装側にある

「rules から作ったページ」で一括りにしないこと。同じ ingest で生まれた姉妹ページでも段が変わる。

### 因果・規範の主張に実測表が付いているとき（頻出する境界・2026-09-02）

R2 の「因果・規範・一般化は上限 `reasoned`」と、§序列 rank 4 の「対象を走らせた / 状態を変えて
結果を観測した」は、**実測表を持つページで正面から衝突する**。実測 2 者に同じ 5 ページを振ったとき、
不一致 2 件はどちらもこの境界だった（一致率 3/5）。

**測っている対象が「主張そのもの」か「主張の前提」かで割る:**

- **主張＝対象の挙動そのもの**で、入力を変えて出力を観測した表がある → **`tested`**
  （例: 主張「ブランチ名の区切りを `_` 以外にすると番号抽出が壊れる」＋ ブランチ名 5 通り ×
  実際のフック出力の表。走らせた結果が主張の本体）
- **主張＝こう判定 / 対処すべきという規範**で、実測は「既存のやり方では駄目」を示す前提 → **`reasoned`**
  （例: 主張「全リモートブランチとタグの指すコミットで判定せよ」＋ 4 指標が嘘をつく実例。
  提案した方法の正しさ自体は測っていない）

📌 **判定の問い: その表を消したら、主張は主張でなくなるか。**
なくなるなら `tested`、「根拠が弱くなるだけ」なら `reasoned`。

R2 の例外（A/B 比較・前後比較・復旧確認）は**改修の効果**を測った場合の話で、
この境界はそれとは別 —— 改修していないページでも、挙動そのものを観測していれば rank 4 に届く。

## 鮮度（stale）の扱い

**段に鮮度を混ぜない。** `is_stale` は `evidence_at`（無ければ `updated`）から計算する computed overlay。

| 対象 | 閾値 | 扱い |
|---|---|---|
| rank 5・6（人間） | 90 日 | 警告する（人間の再承認は高いので古さが効く） |
| rank 3・4（`tested` / `sourced`） | 90 日 | **再検証を促す**（降格させない。AI の再検証は安い） |
| rank 1・2（`reasoned` / `draft`） | — | 対象外（元から低く、古さが情報を足さない） |
| `index` | 90 日 | 警告する（索引は鮮度が本質） |
| `stated` / `verbatim` / `disputed` / `archived` | — | 対象外 |

## 書き手（ingest skill）の既定値

新規ページは **`draft`** で書く。これは**下限**であって固定値ではない。

証拠が本文にあるなら、このルーブリックに従って上の段へ上げてよい。**上げるときは `lifecycle_evidence` と
`evidence_at` を必ず書く**（書けないなら上げる根拠が無い ＝ `draft` のまま）。

更新のときは既存の `lifecycle` を維持する。**証拠が増えたときだけ**、その証拠を `lifecycle_evidence` に
書いて上げる。隣のページの値を真似て決めてはいけない —— それが 2026-08-12 に 66 ページを汚染した経路。

## 一括判定を並列で流すときの規約

1. **入力はこのファイルだけ**。各 skill の SKILL.md から基準を引かせない
2. **主張（R1）を出力必須にする**。段より先に書かせる
3. **決定表を渡す**（自由記述にしない）
4. **`lifecycle_evidence` と `evidence_at` を出力必須にする**（人間が後から検算できる）
5. **キャリブレーションを先に走らせる** —— 同じ数ページを 2 者に重複で振り、一致率を測る。
   不一致はこのファイルへ追記してから残りを流す。**全件を一発で流さない**
6. **決定表に無い型が出たら止めて人間へ上げる**

### 一括移行の実測 —— このルーブリックが効くかの答え

**判定は安価なモデルで足りた。** キャリブレーション（同じ 6 ページを 3 者へ独立に振る）は **6/6 で
全一致**、本判定 71 件も保留 0 件で通った。ルーブリック導入前に同種の判定を上位モデル単体でやった
ときは 24 件中 8 件しか一意に決まらなかった —— 同じ vault・同じ作業で、変わったのは基準だけである。^[extracted]

> **一般則: 判定がブレるとき、まず疑うのは基準であってモデルではない。**
> 決定表と「主張を先に書く」規則を入れた時点で、判定は安価なモデルでもほぼ決定論的になった。
> モデルを上げる前に、基準が一意に決まる形になっているかを確かめる方が安く効く。 ^[inferred]

ただしキャリブレーション自体を省く根拠にはならない —— **6/6 だったことは走らせて初めて分かった**。
次に大量判定を流すときも、まず数ページで一致率を測る（コストは全体の 1 割未満）。
⚠️ **前回の分布を目標値として使わないこと** —— 分布は母集団で変わる（後日の別バッチでは `tested` 比率が
44% → 16% に落ちたが、判定の甘辛ではなく残っていたページの型の差だった）。^[extracted]
